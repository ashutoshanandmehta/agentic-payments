Delegated payments · walkthrough

From Intent to Settlement

What happens, in order, when an AI agent tries to pay a ₹499 invoice — and the one check that decides whether the user gets charged what they agreed to.

The sequence

Seven stages

Stages 0 to 2 happen before any money is at risk. Stage 3 is where a payment is refused or allowed. Stages 4 to 6 are the rails.

03

Three gates, in this order

Each gate answers a different question, and all three must pass. A gate that fails stops the payment before anything reaches the rails.

Order gate this thesis

Knows what the user agreed to buy. Checks that the amount and the payee still match the signed order, that the order adds up, and that it is not stale.

Mandate

Knows what the user permitted. Is it active and in date, is this payee in scope, is the amount under the ceiling, is there headroom left in the cap.

Policy

Knows what the operator permits. A global ceiling, a daily total, a velocity limit, duplicate suppression, and a floor on the agent's own confidence.

The order gate runs first on purpose. "Can they afford it" is a different question from "did they agree to it", and only the second one notices a ₹600 charge against a ₹118 basket.

04

Two legs, not one

The money leaves the payer, sits in a suspense account, then arrives. Between the two legs it is real, has left one bank, and has not reached the other.

Mandate headroom is consumed after the debit succeeds — not at authorisation, which would let a failed payment permanently eat the user's cap, and not at settlement, which would let two payments both pass the same limit.

05

Reconciliation resolves what was left stranded

A sweep asks both banks what actually posted, and acts on the answer. It is idempotent, so running it twice changes nothing.

Debit postedCredit postedWhat the sweep does
yesyesComplete it — the payment settles
yesnoReverse it, return the money, release the mandate headroom
nonoNothing to undo — mark it failed
06

The books are audited

Every balance is re-derived from the ledger entries rather than read from a stored number. Each transaction's entries must net to zero, the whole ledger must net to zero, and the suspense account must be empty — nothing left in flight.

Why the order gate exists

The same payment, run both ways

The user agreed to a basket of ₹118. The agent asks for ₹600 from the same shop. The mandate allows ₹1,000 a payment, so nothing about the limits is violated.

The mandate and the policy both pass, because neither of them holds any record of what the user agreed to buy. That record is the missing piece.

The finding on signatures. A self-consistent inflated order — one whose lines really do add to ₹600 — is approved whether the agent signs it, the shop signs it, or both do. A signature proves who wrote a record, not that the record is true. What actually refuses it is a per-payment ceiling close to the real basket size.

Run it yourself: python src/cli.py consent for the comparison above, python src/cli.py --fresh demo for the full lifecycle. 60 tests pass — 44 on the rails, ledger and reconciliation, 16 on the order gate. Simulated rails throughout: no real NPCI connection, no settlement windows, no UPI PIN cryptography.
